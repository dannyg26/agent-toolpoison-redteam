## Proposed design for the follow-up run (heretic arm and any rerun)

1. **Scope:** one arm per pod session, each with its own cap and approval. Use the same GPU SKU and vLLM version. Install from a constraints file (`pip freeze` captured), and record the resolved Hub commits for model, tokenizer and judge.
2. **Incremental, resumable generation:**
   - Shuffle all items by `sha256("run1c:"+id)` and split them into shards of about 250.
   - For each shard: run step 1, then that shard's InjecAgent step 2. Write `<arm>/shard-NNN.jsonl` and fsync, then write `shard-NNN.done` with its SHA-256.
   - On restart, skip completed shards.
   - Pre-register the partial-arm rule. Because shard order is random, an arm stopped mid-way is a random subsample; either score the completed shards with stated denominators, or keep "unobserved" and only use the shards to resume on a new pod. Choose one before launch.
3. **Pull as you go:** each poll downloads new `.done` shards (tar of the new files only), so a hard stop loses at most one shard.
4. **Measured abort rule:** after the first 2 shards, project the finish time from measured tokens per second. If it is past the soft stop, stop and record "insufficient time" *before* spending the rest (decided on timing alone).
5. **Judge off the critical path:** do not judge on the paid pod after all arms. Either run the Gemma-2B judge locally in WSL on the downloaded answers, or on the pod right after each arm. Re-judge all three arms in one pinned pass (R1-07).
6. **Retry only on load failure:** use the `<arm>.loaded` marker (R1-13).
7. **Throughput levers that leave frozen generation settings unchanged:** explicit `max_num_seqs` / `max_num_batched_tokens`; order shards with mixed `max_tokens` so the tail is shorter. Do **not** change FP8, the context length, the token caps or the sampling settings.
8. **Freeze hygiene:** a new `run1c_freeze.json` that pins `run1_freeze.json`; the execution log kept outside frozen files (R1-03).
